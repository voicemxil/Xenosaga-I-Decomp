# The final link

How `build/SLUS_204.69.elf` is produced, why it is byte-for-byte identical to
the retail executable image, and what to check when that stops being true.

**Current status: the flattened build is byte-identical to the retail image.**
3,082,476 / 3,082,476 bytes, SHA-1 `ba1132845398d91cd9a921e92965eb51d915ec8b` —
the same hash `config/SLUS_204.69.yaml` declares for the target. Verify with
`ninja check`.

That is a statement about the *image*, not about the decompilation: the vast
majority of those bytes still come from `asm/`, not from `src/`. Whole-image
identity means the link is correct and every assembled/compiled object lands at
its original address; `tools/verify.py` is what measures how much real C is
behind it.

---

## 1. Two different questions, two different tools

| | question | tool |
|---|---|---|
| per function | does this decompiled C emit the original instructions? | `tools/verify.py` |
| whole image | is the linked executable byte-identical to the retail one? | `tools/verify_elf.py` (`ninja check`) |

They can disagree in both directions. `verify.py` reads the *original* ELF for
expected bytes, so it keeps passing even when the link is completely broken —
which is exactly what happened before this was fixed. `verify_elf.py` links the
real thing and diffs the whole image, so nothing hides.

## 2. Pieces of the link

```
build/asm/**/*.o        assembled from asm/    (not yet decompiled)
build/src/**/*.o        compiled from src/     (decompiled C)
build/assets/**/*.o     .incbin of raw data blobs
        |
        |  mips64r5900el-ps2-elf-ld --allow-multiple-definition -m elf32lr5900
        |  -T config/SLUS_204.69.pinned.ld
        v
build/SLUS_204.69.elf
```

### The linker script

`config/SLUS_204.69.pinned.ld` is the authoritative script and is **tracked in
git**. It starts with four INCLUDEs:

```
INCLUDE "config/undefined_funcs_auto.txt";   /* Splat: func_ADDR = 0xADDR;   */
INCLUDE "config/undefined_syms_auto.txt";    /* Splat: D_ADDR   = 0xADDR;    */
INCLUDE "config/symbol_addrs.txt";           /* Splat: named symbol table    */
INCLUDE "config/linker_script_extra.ld";     /* hand-maintained supplement   */
```

This is how Splat-style symbol files reach `ld`: they are plain
`name = 0xADDR;` assignment statements, valid linker-script syntax, pulled in
by INCLUDE. There are no `--defsym` flags and there is no generated stub
object. If those INCLUDEs are absent, every reference to a hardware register,
an unextracted function, or an address with no owning object becomes an
undefined reference.

`config/linker_script_extra.ld` holds what Splat does not generate:

* `ENTRY(ENTRYPOINT)` — pins `e_entry` to `0x200008`, matching the retail ELF.
* Seven absolute addresses referenced by the ov02 overlay (`D_100020`,
  `D_100060`, `D_1000010`, `D_1245C58`, `D_2A007F8`, `D_490DC0`, `D_4A1A92`).
  These are bare `%hi`/`%lo` pairs with no label at the target — EE hardware /
  physical-memory addresses, plus two unaligned interior offsets into `.data`
  that have no symbol of their own. The values were confirmed against the
  encoded `lui`/`addiu` immediates in `asm/ov02/2DD000.s`.

Keeping these in a separate, hand-maintained file matters: the three
`*_auto*`/`symbol_addrs` files are regenerated by `splat split`, and anything
added to them by hand is lost on the next split.

### Why "pinned"

Splat's generated script (`config/SLUS_204.69.ld`) packs sections
sequentially. Alignment differences of a few bytes then shift every downstream
section, which breaks `$gp`-relative relocations and puts the whole image out
of position. The pinned script instead fixes each output section at its exact
retail virtual address (`.cod_data 0x338600`, `.cod_rodata 0x4BE280`,
`.cod_lit4 0x4D7B80`, `.cod_sdata 0x4D8A00`, `.cod_bss 0x4DC500`,
`.cod_bss2 0x4DC880`, `.ov02 0xA00000`), so a size wobble inside one section is
absorbed by that section's padding and nothing downstream moves.

Load addresses (`AT(...)`) are pinned the same way. `ov02_ROM_START` is
hard-coded to `0x2DD000` rather than following the running `__romPos`: the
retail ELF pads the loaded `cod` image (which ends at ROM `0x2DC4E0`) out to
`0x2DD000` before the overlay. Letting `__romPos` decide shifts ov02 `0xB20`
bytes early in the flattened image.

The `.ov02` output section also deliberately omits the trailing
`. = ALIGN(., 16)` statements that every other segment has. The retail ov02
section is `0x138EC` bytes and ends 4-byte aligned; an `ALIGN` advances the
location counter even when the input section is empty, which padded the image
4 bytes past the retail size.

## 3. The failure mode this replaced (do not reintroduce it)

Until this was fixed:

* `LDFLAGS` carried **`--noinhibit-exec`**, which tells `ld` to write an output
  file *even when the link failed*. `ld` exits 0, ninja records success, the
  build is green.
* The `ld` rule used `config/SLUS_204.69.ld` — Splat's generated script, which
  is **untracked** and has **none of the INCLUDE lines**. `tools/post_split.sh`
  copied the pinned script over it, so the build was correct only if that copy
  step had been run since the last split. One `splat split` without it silently
  reverted the link.
* Both together meant the ELF had been full of unresolved references
  (`D_8000`, `D_70000020`, and dozens more) with nothing reporting it, while
  `tools/verify.py` — which reads expected bytes from the *original* ELF —
  kept printing a healthy pass count.

The fixes, in order of importance:

1. **`--noinhibit-exec` is gone.** A failed link fails the build. The rule also
   `rm -f`s the output on failure so no stale ELF can be mistaken for a fresh
   one.
2. **The `ld` rule names `config/SLUS_204.69.pinned.ld` directly.** The copy
   step is no longer load-bearing; `config/SLUS_204.69.ld` is now an inert
   Splat artifact.
3. **The four INCLUDEd files are ninja implicit deps of the link**, so editing
   a symbol address relinks.
4. **`tools/post_split.sh` warns** if Splat's generated script gained an input
   section placement the pinned script lacks — the one thing the removed copy
   step used to hide.
5. **`ninja check` diffs the whole image** and fails on any difference.

### Expected warnings

The link prints a run of

```
warning: alignment 1 of symbol `foo' in build/asm/data/cod/004DC880.bss.o
         is smaller than 16 in build/src/.../bar.o
```

These are benign. The `.bss`/`.sbss` placeholder objects declare symbols with
alignment 1 while the decompiled C declares the same objects with their natural
alignment. Because every address is pinned by the linker script, the weaker
alignment never actually moves anything. They disappear as `.bss` ownership
migrates from `asm/` to `src/`.

## 4. Whole-image verification

```bash
ninja check                              # strict: any difference fails
python3 tools/verify_elf.py              # summary + first mismatch ranges
python3 tools/verify_elf.py --per-section
python3 tools/verify_elf.py -n 50        # more mismatch ranges
python3 tools/verify_elf.py --save build/SLUS_204.69.bin
```

`verify_elf.py` runs `objcopy -O binary --gap-fill=0x00` on the built ELF and
diffs the result against `config/SLUS_204.69.rom`, reporting total bytes,
matching bytes, a per-section breakdown, and mismatch ranges annotated with the
symbol each one falls in.

### The reference image

`config/SLUS_204.69.rom` is the two loaded regions of the retail ELF laid end
to end — exactly `elf/SLUS_204.69[0x1000 : 0x2F18EC]`, i.e. `.text` through the
end of the ov02 overlay, 3,082,476 bytes.

**`objcopy -O binary` on the *retail* ELF does not produce this**, despite what
older SETUP.md instructions said. The retail ov02 LOAD segment has PhysAddr
`0xA5B8F8` (not `0x2DD000`), so `objcopy` leaves a ~5.7 MB hole and emits an
8.4 MB file. Regenerate the reference with:

```bash
python3 tools/verify_elf.py --make-rom
```

`objcopy` *is* correct on the **built** ELF, because the pinned script's
`AT(...)` expressions make its load addresses the ROM offsets directly.

## 5. The ov02 overlay

`ov02` is a separately loaded overlay: virtual address `0xA00000`, ROM offset
`0x2DD000`, `0x138EC` bytes, containing the `Umn*` menu / title code.

It **is** fully extracted — `asm/ov02/2DD000.s` is 18,724 lines of real
disassembly ending at `UmnEventTextInit`, with its data tail in
`asm/data/ov02/2EC680.data.s`. (An earlier note describing it as a
~2000-line placeholder is stale.) It links and matches byte for byte; nothing
is missing from the image on its account.

Two ov02-specific quirks are recorded above and worth re-reading before
touching the script: the pinned `ov02_ROM_START = 0x2DD000`, and the omitted
trailing `ALIGN`s.

## 6. Toward a bootable image in PCSX2

The flattened image already matches, so the remaining work is packaging, not
correctness.

`build/SLUS_204.69.elf` differs from `elf/SLUS_204.69` in *container* only:

| | retail | built |
|---|---|---|
| entry point | `0x200008` | `0x200008` (pinned via `ENTRY`) |
| `.text` file offset | `0x1000` | `0x1000` |
| ov02 file offset | `0x2DE000` | `0x2DE000` |
| LOAD segments | 4 (+ REGINFO) | 4 |
| sections | 57 | 13 |
| size | 3,441,932 | ~4.1 MB |

The size and section-count differences are entirely non-loaded metadata: the
retail ELF carries `.reginfo`, `.mdebug.eabi64` and ~40 `.DVP.ovlytab` /
`.DVP.overlay[...]` VU-microcode sections; the build carries a much larger
`.symtab`/`.strtab` instead. None of it is in a LOAD segment, so none of it
reaches memory. The remaining differences to close, in order:

1. **ov02 LOAD PhysAddr.** Retail uses `0xA5B8F8`; the build uses `0x2DD000`
   because that is what makes `objcopy` produce the comparable image. A PS2
   loader reads `p_offset`/`p_vaddr`, not `p_paddr`, so this is very likely
   irrelevant at runtime — but it is the one loadable-header field that
   differs, so check it first if the overlay misbehaves.
2. **`.DVP` VU-microcode sections.** Not loaded by the ELF loader, but the game
   locates VU microcode through the `.DVP.ovlytab` table. If anything VU-side
   fails, this is the cause, and the fix is to carry those sections through
   from the original rather than re-emit them.
3. **Strip before running.** `mips64r5900el-ps2-elf-strip` on the built ELF
   takes it from ~4.1 MB to 3,087,108 bytes — *below* the retail 3,441,932,
   because retail carries the `.DVP` sections the build does not. The stripped
   ELF still passes `verify_elf.py --strict`, entry point still `0x200008`.

Two routes to actually running it:

* **PCSX2 Run-ELF.** Boot the retail ISO first so the CD/DVD device and the
  game's data files are present, then use *Run ELF* on the built (stripped)
  ELF. Fastest iteration loop; no ISO rebuild.
* **Patch it into the ISO.** `SLUS_204.69` sits at a fixed LBA in the ISO's
  ISO9660 image. Because the *loaded* bytes are identical, the safest patch is
  not to replace the file wholesale but to write the built image's bytes over
  the retail file's loaded regions in place (ISO offset of `SLUS_204.69` plus
  `0x1000`, `0x2F08EC` bytes). Same length, so no directory-record or LBA
  churn.

Neither is exercised yet. Since the image already matches byte for byte, a
successful boot proves the packaging, not the decompilation.
